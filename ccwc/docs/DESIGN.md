# ccwc — Design

## Assumptions (stated before coding, per ponytail)

1. Language: Python 3, standard library only, single file `ccwc.py`.
   Reason: fastest to verify, portable, no build step, and the
   challenge allows any language. No framework, no dependency.
2. Input is read as bytes, in 8 KiB chunks, never loaded whole.
   Reason: `wc` must work on gigabyte files with constant memory.
   The earlier streaming lesson from the wc challenge write-ups
   applies here: chunk, update counters, discard the chunk.
3. Only the challenge scope is built: `-c -l -w -m`, default,
   one file or stdin, plus the multi-file total line (small, same
   code path, and it is real `wc` behaviour).
4. Ask-matt / ponytail skill files: at build time the ask-matt
   install was still running with no output, and ponytail was
   never confirmed installed (2026-10-14 attempt, no files found).
   The ponytail behavioural guidelines recorded in memory are
   applied anyway: think first, minimum code, surgical changes,
   verifiable success criteria. If the skill installs later, the
   next project re-checks it before coding.

## Algorithm

Single pass, one state machine, per input stream:

```
bytes = lines = words = chars = 0
in_word = False
decoder = incremental UTF-8 decoder (for -m only)

for chunk in stream (8192 bytes):
    bytes += len(chunk)
    lines += chunk.count(b'\n')
    chars += len(decoder.decode(chunk))
    for byte in chunk:
        if byte in whitespace:
            in_word = False
        elif not in_word:
            words += 1
            in_word = True

chars += len(decoder.decode(b'', final=True))
```

Notes:

- Word counting is a two-state machine, not a split. Splitting
  would need the whole file in memory and would mishandle a word
  split across chunk boundaries. The `in_word` flag carries across
  chunks, so a word split across an 8 KiB boundary is counted once.
- Character counting uses an incremental decoder for the same
  reason: a multibyte UTF-8 character split across chunks must not
  be counted twice or dropped. Invalid UTF-8 bytes are counted as
  one character each (decoder with `errors="replace"` would do the
  same for display, but here we count the replacement as one
  character per invalid byte sequence — documented, and only
  reachable on non-UTF-8 input).
- Lines, bytes, and words are counted from bytes, so they are
  independent of locale and decoding.

## Output formatting code path

1. Count every input stream first, store only its four counts.
2. Compute display width:
   - stdin, more than one count: 7 (GNU behaviour).
   - one count: its own digit length (i.e. no padding).
   - files, more than one count: digits of the total byte count
     summed over all files given (see SPEC.md for the verification).
3. Format each count with `str(count).rjust(width)`, join with
   a single space, append ` <filename>` for files, nothing for
   stdin. Append a `total` line when more than one file was given.

## Success criteria

- `python3 -m unittest discover -s tests -v` passes.
- For `-c -l -w`, default, and stdin `-l`, output matches system
  `wc` on the same inputs (same files, same order).
- For `-m`, output matches the expected UTF-8 code-point count
  (see SPEC locale note).
- Empty file, no-trailing-newline file, and UTF-8 file are all
  covered, not just the happy path.
